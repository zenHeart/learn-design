# 我的设计哲学：清晰、克制与有效空间

我希望打开工作台就知道什么值得关注、谁在推进、哪里需要我判断；查看细节后还能接着工作。
视觉身份要稳定，空间留给有用的信息，自动化的状态要可信。

以下是从 2026-09-09 至 2026-09-10 的工作台反馈整理出的个人判断方法。[S1]
它适用于持续操作和观察的工作型界面，不是所有网站的模板；外部标准只约束其明确涉及的部分。
产品的状态合同、尺寸参数、代码和运行证据由产品仓库维护，这里不复制实现规范或私有材料。

## 1. 先定义用户要回答的问题

功能导航决定“做哪类工作”，模块决定“处理哪一部分”，观察维度决定“同一批对象怎么看”，
筛选决定“只看哪些记录”。我希望界面按这四个问题组织，而不是把所有可以切换的选项都做成 Tab。

| 层级 | 例子 | 判断 |
| --- | --- | --- |
| 功能 | 工作台、资源、看板、文档 | 用户工作目的不同 |
| 模块 | 运行、模型额度、职责 | 同一功能内有独立内容与操作 |
| 观察维度 | 机器、项目、会话 | 同一批记录按不同对象组织 |
| 筛选 | 本周、全部范围、实体机、云主机 | 改变记录范围，不创造模块 |

我的布局约定是：左侧功能导航，右侧按需显示模块栏；共用操作与模块标签同排，
其下是当前模块的工具栏和主工作区。只有一个模块时直接从工具栏开始，周期与范围放在一起。
这是一套信息架构选择；WAI-ARIA 对 Tabs 的面板关联和键盘行为另有要求。[S2]

**检查：** 改变选项后，用户是换了工作内容、观察角度，还是记录范围？控件应表达真实差别。

## 2. 最显眼的位置留给下一项判断

我关注目标是否在推进、什么卡住了、下一步是否需要我介入。
没有内容的“本周承诺”、标签设置教程和无关的总记录数，不应长期占据最重要的摘要区。

有明确目标或承诺时展示真实对象和关联工作；没有时收起占位，不代替我指定承诺。
需要我验收、决策或解除阻碍的事项优先呈现，并给出对象、短原因和下一步入口。
任务计数可以描述过程，但不能冒充目标达成率。

Linear 将项目状态与项目健康分开表达；Atlassian 的状态更新强调进展、阻碍及需要的帮助。[S6][S7]
我借鉴的是其问题顺序，不是把所有产品都套进同一组红黄绿状态。

**检查：** 读完摘要能否决定接下来查看什么？如果只是知道“某个字段还没填”，它是否值得占据主位？

## 3. 用结构去重，保留必要含义

导航只显示图标与名称；动态计数和说明放回工作区。选中导航已经说明页面身份时，
全局顶栏和正文不重复页面名、英文译名或同义介绍。全局目标有真实内容才显示，没有时收起占位。

高频操作直接可见，低频解释按需读取。关闭这样熟悉的动作可以只显示图标，仍要保留可访问名称、
键盘焦点和足够的命中区域。陌生、有后果或可能误解的动作保留文字；不把“删除文字”当成目的。

**检查：** 去掉一个元素后是否仍能定位和理解？若删掉的是异常原因、来源范围或草稿边界，就需要另一条可靠入口。

## 4. 让工作关系先于技术编号

运行监控先让我看到“机器 → Agent → 项目 → 任务”。容器说明承载关系，缩进和对齐说明归属，
简短的任务标题说明正在做什么。进程号、完整路径与诊断留给详情。

同一批工作可以按机器、项目或会话组织。机器适合看承载，项目适合看投入，会话适合找执行实例；
切换维度不应偷偷改变事实口径。不能因为目录同名就合并项目，也不能把配置身份当成正在工作的实例。

**反例：** 精确数值比较适合表格，复杂依赖适合关系图。卡片和头像不是所有监控场景的固定答案。

## 5. 可信状态比丰富状态更重要

我要求机器连接、服务健康、Agent 活动、任务结果分别表达。绿灯必须指向明确对象和新鲜证据。
服务可达不代表所有 Agent 忙碌，进程存在不代表正在执行任务，执行结束不代表人已验收。

已采集的零值、没有采集、读取失败和数据过期不能混为一谈。
离线、不可达、空闲也有不同含义。没有有效数据时保留身份和必要异常，不铺一组空仪表。
刷新失败可以保留旧信息，但不能更新时间制造“刚刚观测”的印象。

**检查：** 切断数据后会不会继续显示正在工作？相同记录在图标、计数、筛选和详情中是否一致？

## 6. 图形承担比较，动效承担变化

我偏好 ServerCat 式紧凑图形与 Grok Bot 式身份、活动表达。[S1]
借鉴前先确定图形回答什么：状态图标帮助定位，比例条比较有分母的量，曲线展示有时间序列的变化。
没有分母和比较价值的圆环应当删除；不能因为参考产品有仪表就补造数据。

Grok Bot 通过一致的基本形状与有控制的差异保持身份可辨，并用角色动作表达活动。[S5]
我的转化是：身份稳定、动效有限、证据过期即停止；暂停动效后仍能读懂状态。
不会把所有角色持续运动当作“系统自发运行”的证明。

状态可以少写重复的“正常”，但不能只靠颜色传意；提供形状、符号或文字，符合 WCAG 的颜色使用要求。[S3]
完整含义不能只对鼠标悬浮开放，键盘和触屏也需要可靠的读取入口。

**检查：** 去掉颜色和动效后还分得清吗？每张图是否有明确单位、范围和比较对象？

## 7. 阅读是密度的前提

认可主题后，优化延续它的色彩、材质、字体角色与边界语言。
字体太小或模糊时先查字阶、字重、回退字体、对比度和缩放，不用换主题或继续缩小整页解决。
中文说明、控件、标题和编号各有稳定角色，不能全部挤成一样小的元数据。

密度通过去重、分组和合理重排获得。砖块布局避免为对齐填满空行，但保留一致间距；
有业务语义的看板状态列可以为空。长文本合理换行或省略，并提供完整内容；关键差异不能被截掉。

**反例：** “充分利用空间”不等于零留白，更不等于全部信息必须塞进首屏。分组、呼吸和稳定结构本身有价值。

## 8. 渐进查看必须保住阅读位置

我偏好“总览 → 侧栏 → 主动全屏”的查看路径。摘要给出判断信息，侧栏给出细节，
需要专注阅读时再全屏。默认点击对象不应把我直接带离正在比较的列表。

返回后恢复维度、筛选、选中对象和滚动。侧栏与全屏应是同一对象的两种呈现，不能出现两套不同数据。
模态交互的焦点进入、限制背景交互、Escape 关闭与焦点返回遵循 WAI-ARIA。[S4]
需要同时操作背景时，应评估非模态检查器；侧栏并不是所有详情的唯一解。

**检查：** 完成打开、全屏、返回、关闭后，能否立即接着刚才的工作？

## 9. 稳定性验收不能只看 CLS

打开详情不应让砖块卡片增高并搬到另一列；切换模块不应让外壳宽度和工具栏位置跳变；
实时更新不应持续改变对象排序。主动筛选、改变观察维度或调整窗口大小则可以合理重排。

CLS 排除了部分近期输入引起的布局位移，因此分数为零仍可能丢失阅读位置。[S8]
我要求同时检查元素边界、滚动、焦点和完整返回路径，不用长页占位或裁切遮住问题。

**检查：** 静态截图之外，是否实际走完了产生问题的交互？有无长内容、窄屏和刷新场景？

## 10. 流程图要区分分工、交接与事实

组织图解释谁负责，流水线解释如何交接，执行记录解释实际发生了什么。
我希望图形把这几种关系说清楚，而不是用一张复杂图包揽全部信息。

标题、节点、连线和工具区各有空间；碰撞应在布局中修复，不能只移动文字掩盖问题。
可编辑图表要说明是草稿还是业务配置，预览和导出也应保留这一区别；改图不能暗中改变任务分发。

**检查：** 用户能否区分计划关系和真实执行？屏幕与导出是否都没有遮挡？

## 11. 将品味变成可验证的判断

一条可复用规则需要说明：适用的工作、解决的问题、可能的反例、如何检查。
产品选择不能冒充普适标准：默认本周全部、两类机器分组、具体字号与按钮尺寸都应留在产品合同。

正式文档保留当前有效规则与边界；同一条规则改变时替换旧描述，不在后面叠加相反结论。
检查顺序保持为工作目标、信息关系、交互、视觉、真实验证。局部测试和主观舒适感都不能证明全站通过或效率提升某个百分比。
