# 设计评审：从硬红线到协作礼仪

> 取用日期：2026-09-20；来源层级：L0（W3C、Material Design、Apple HIG、NN/g）、L2（Smashing Magazine、WebAIM）、L4（Refactoring UI）。
> 核心信源：WCAG 2.2 [S1]、Nielsen 10 大可用性启发式 [S2]、Material Design 3 [S3]、Apple HIG Accessibility [S4]、WebAIM [S5]、Refactoring UI [S6]、NN/g Heuristic Evaluation [S7]、Smashing Magazine Design Critique [S8]。

---

## 本章目标

完成本章后，你应能够独立完成下列可验证行为：

- 区分 Stakeholder review / Peer critique / Heuristic evaluation 三种评审类型的适用场景与产出差异。
- 按"上下文 → 走查清单 → 缺陷归因 → 优先级"四步流程执行一次完整评审，并产出结构化报告。
- 用 WCAG 2.2 AA 与平台规范（Material/HIG）建立硬红线拦截清单，对 P0 缺陷立即阻断。
- 选取 Nielsen 10 启发式中与日常项目最相关的 6 条作走查问句，并应用到真实界面。
- 列出 8 类常见视觉缺陷模式（8pt 网格偏离、对齐断层、字阶断层、色彩滥用、间距呼吸感差、信息密度失衡、可访问性硬伤、组件状态缺失）并各举一例。
- 撰写一份合格的评审记录：截图 + 缺陷描述 + 严重度 + 修复建议 + 验收标准。
- 在评审协作中维持"对事不对人、先肯定再建议"的工程礼仪。
- 把评审产出对接 style-refactor 流程，形成可执行的修复任务清单。

## 一、设计评审的三种类型

### 1. Stakeholder review（利益相关者评审）

由产品经理、业务方、品牌方、市场方、客服代表组成的评审，目的是确认设计是否满足业务目标、品牌一致性与可运营性。典型问题：

- 这个页面对销售线索转化的关键信息是否突出？
- 文案是否与品牌语调手册一致？
- 客服反馈的高频投诉是否被考虑？

**注意**：Stakeholder 评审产出的是业务约束，不是美学判断——评审人有权否决"偏离品牌"的方案，无权以"我更喜欢蓝色"否决"用品牌色"的设计。

### 2. Peer critique（同行评审 / 设计内审）

设计师与设计师之间的专业评审，目的是提升视觉秩序、交互一致性、信息架构合理性。典型问题：

- 间距是否符合 8pt 网格？
- 同类组件在不同页面是否保持一致？
- 信息层级是否清晰？

**注意**：Peer critique 的反馈必须挂载具体指标（网格、对比度、雅各布定律），不能停在"我觉得"。

### 3. Heuristic evaluation（启发式走查）

由可用性专家对照公认启发式（最常用 Nielsen 10 条）逐项排查界面是否符合通用原则 [S2][S7]。与 Peer critique 的区别是评审依据来自**外部公认标准**而非团队内部约定。

- 适用于：无设计同事的小团队、跨团队协作、关键页面上线前体检。
- 成本：单人 30–60 分钟即可走查一个核心页面。
- 局限：专家可能漏掉业务上下文，因此通常作为 Stakeholder review 的前置环节。

工程实践中，三种评审应**按顺序组合**：Heuristic evaluation（找硬伤） → Peer critique（找改进点） → Stakeholder review（找业务偏离）。

## 二、四步评审流程

### 1. 第一步：上下文确认

不读上下文就开评 = 用通用偏见覆盖具体场景。开工前明确：

- **产品阶段**：MVP 内测？正式上线？大版本改版？
- **用户群体**：开发者？运营？消费者？年龄与无障碍需求？
- **业务目标**：该页面的核心 KPI（转化率、留存、付费率、错误率）？
- **平台**：Web？iOS？Android？桌面？响应式断点范围？

依据产品类型矩阵（落地页 / B2B SaaS / 移动 App / AI 对话）确定第一优先级约束。详见 [docs/patterns/product-patterns.md](../../patterns/product-patterns.md)。

### 2. 第二步：走查清单

按 [docs/workflows/design-review.md](../../workflows/design-review.md) 的四步闭环流执行：

1. 定位产品形态与约束
2. 致命可用性红线排查（WCAG AA）
3. 交互秩序与启发式走查（Nielsen 10）
4. 心理学归因与报告输出

每一条走查问题对应一个"是 / 否 / 部分"判定，并附截图证据。

### 3. 第三步：缺陷归因

把每条缺陷归到三类根因之一：

- **硬合规违反**：WCAG 4.5:1、平台规范（Material/HIG）、品牌强制条款。无讨价还价空间，直接 P0 阻断。
- **启发式违反**：Nielsen 10 条中的某一条被破坏。优先级视严重度而定（P1–P3）。
- **风格优化**：不违反任何硬规则，但视觉秩序、信息密度、组件复用度有改进空间。P2–P3。

归因清楚后，修复建议才不会被反驳成"个人偏好"。

### 4. 第四步：优先级与可执行性

按 P0 / P1 / P2 / P3 分级：

| 级别 | 含义 | 处置 |
|---|---|---|
| P0 | 合规阻断、无障碍阻断、品牌强制违背 | 立即修复，阻断上线 |
| P1 | 启发式严重违反（如状态不可见、错误无出口） | 当前迭代必须修复 |
| P2 | 视觉秩序、信息密度、组件一致性 | 下一迭代修复 |
| P3 | 风格微调、文案打磨 | 排期修复或归档 |

每条缺陷的修复建议必须包含**可执行的验收标准**——例如"调整文本色至 `#52565C`，使对比度 ≥ 4.5:1"，而不是"调整文本色让它更清晰"。

## 三、硬红线拦截

以下条目不通过直接判定 **P0**：

### 1. WCAG 2.2 AA 红线 [S1]

- 正文文本对比度 ≥ 4.5:1
- 大文本（≥18pt / ≥14pt 粗体）对比度 ≥ 3:1
- 非文本组件（图标、控件边界、焦点指示器）≥ 3:1
- 触控目标 ≥ 24×24 CSS px
- 键盘焦点可见，未被遮挡（WCAG 2.2 新增 2.4.11）
- 拖拽操作必须提供单指针替代（WCAG 2.2 新增 2.5.7）

### 2. 平台规范红线 [S3][S4]

- **Material Design 3**：组件尺寸遵守 M3 token（48dp 标准触控区），动效时长 ≤ 500ms。
- **Apple HIG**：44×44pt 最小触控区、Dynamic Type 必须支持、安全区（Safe Area）完整。
- 冲突时以 WCAG 为合规底线，平台规范为日常依据。

### 3. 品牌一致性红线

- 主色（品牌色）是否被滥用为 success / warning / error 等语义色（语义色应独立）[S6]
- Logo 是否被拉伸、变形、放置在低对比度背景上
- 字体是否使用了品牌规范外的字体

## 四、Nielsen 启发式：6 个最常见误区

完整 Nielsen 10 条见 [docs/principles/heuristics-wcag.md](../../principles/heuristics-wcag.md)。本节聚焦日常项目中最常被违反的 6 条，并提供具体走查问句。

### 1. 系统状态可见性

走查问句：用户每次操作后，系统是否在 400ms 内给出反馈？

常见误区：

- 提交按钮点击后无 Loading 态，可重复点击。
- 表单提交成功后没有跳转或 Toast，用户不知道发生了什么。
- 长任务（导出、批量处理）没有进度条，用户以为页面卡死。

### 2. 一致性与标准

走查问句：同义操作在站内是否用同一种视觉语言？

常见误区：

- 同一个"删除"操作在不同页面分别用红色文字、红色图标、灰色图标三种表达。
- 主按钮在 A 页面是实心蓝，在 B 页面是描边蓝（违反 Repetition 原则）[S6]。

### 3. 错误预防

走查问句：错误是难以发生，还是发生后再报错？

常见误区：

- 危险操作（删除项目、清空数据）与安全操作（保存、确认）用同色按钮挤在一起。
- 必填字段未在表单开头标注，用户填到末尾才发现漏项。

### 4. 识别而非回忆

走查问句：用户每一屏是否都能看到当前所选内容？

常见误区：

- 多步向导中，上一步填的字段在当前步骤不可见，用户被迫凭记忆重述。
- 筛选器中已选条件被折叠成一行小字，无法快速清除某一项。

### 5. 美学与极简设计

走查问句：当前屏幕的每一个元素是否都服务于当前任务？

常见误区：

- 落地页堆砌五种营销 Banner，首屏看不到核心价值主张。
- 控制台仪表盘塞满所有图表，找不到关键 KPI。

### 6. 帮助用户恢复错误

走查问句：错误信息是否用用户语言 + 给出解决方案？

常见误区：

- 错误提示只说"提交失败"，不告诉用户是哪个字段、为什么失败、如何修复。
- 表单错误用顶部一条 Toast，用户看不到自己填错的那一栏。

## 五、视觉缺陷模式清单（8 类）

按出现频率排序，每类附"如何识别 + 如何修复"：

### 1. 8pt 网格偏离

- **识别**：用浏览器 DevTools 量出 padding / margin / gap，发现 7px、13px、22px 等非 4 倍数。
- **修复**：把所有间距收敛到 4/8 的整数倍，建立 `--space-1: 4px` 到 `--space-16: 64px` 的 token [S6]。

### 2. 对齐断层

- **识别**：连续卡片左边缘存在锯齿状偏移；表格数字未右对齐。
- **修复**：统一基线对齐规则（文本左对齐、数字右对齐、操作列右对齐或居中）。

### 3. 字阶断层

- **识别**：页面出现 14px、15px、16px、18px、20px、22px、24px 等连续字号，无明确档位。
- **修复**：选定 Type Scale 模数（Major Third 1.25 / Perfect Fourth 1.333 / Perfect Fifth 1.5），只保留 4–6 档字号。详见 chapters/02-typography.md。

### 4. 色彩滥用

- **识别**：页面同时出现蓝、绿、橙、紫、粉、红等 6+ 种彩色，每种都用来"强调"。
- **修复**：限制彩色使用到 1 个主色 + 4 个语义色（success / warning / error / info）；其余用灰阶表达层级 [S6]。

### 5. 间距呼吸感差

- **识别**：卡片之间挤在一起，或相反——同一组件内部 padding 大于组件之间的 margin。
- **修复**：保证 `内部间距 < 同组间距 < 不同组间距` 的亲密性法则。详见 foundations/quickstart.md。

### 6. 信息密度失衡

- **识别**：B2B 表格为了"美观"塞入大量留白，导致一屏只能看 5 行；或反过来——营销落地页为了"充实"堆砌文字。
- **修复**：按产品类型矩阵确定第一优先级。B2B 优先信息密度，落地页优先单一价值主张。

### 7. 可访问性硬伤

- **识别**：用 WebAIM Contrast Checker 抽查，发现对比度 < 4.5:1 [S5]；用 Tab 键走一遍，发现焦点环缺失。
- **修复**：把对比度审计加入 CI（与 chapters/01-color.md 中的 Playwright 脚本配合）。

### 8. 组件状态缺失

- **识别**：按钮只有默认态，没有 hover / active / focus-visible / disabled 四态。
- **修复**：每个交互组件必须提供完整 5 态，详见 foundations/quickstart.md 第四准则。

## 六、评审记录模板

```markdown
# 评审对象：[页面/组件名称]
- **评审人**：[姓名 / Agent ID]
- **评审类型**：[Stakeholder / Peer / Heuristic]
- **所属产品类型**：[SaaS / 落地页 / 移动 App / ...]
- **评审日期**：[YYYY-MM-DD]
- **走查结论**：[通过 / 附条件通过 / 阻断拦截]

## P0 阻断性缺陷（合规红线）
- **[对比度不足]** 登录表单辅助提示文字 `#A0AEC0` 在白色背景上对比度 2.8:1，违反 WCAG 2.2 AA。
  - *截图*：附件 issue-001.png
  - *建议修改*：正文灰色调整为 `#52565C` 或加深至 4.5:1 以上
  - *验收标准*：WebAIM Contrast Checker 实测 ≥ 4.5:1

## P1 体验严重缺陷（启发式违规）
- **[缺少状态反馈]** 点击"保存配置"按钮后 1.5s 无 Loading 提示，可重复点击。
  - *截图*：附件 issue-002.png
  - *根因*：违反多赫蒂阈值与状态可见性
  - *建议修改*：点击瞬间将按钮置为 Loading 态并设置 `disabled`
  - *验收标准*：点击后 ≤ 400ms 出现 Loading 反馈

## P2 视觉秩序优化建议
- **[间距节律不一致]** 卡片外部 margin 混用 15px 与 22px。
  - *截图*：附件 issue-003.png
  - *建议修改*：统一收敛至 `--space-4: 16px` 与 `--space-6: 24px`
  - *验收标准*：全站 spacing 通过 4/8 整数倍校验
```

每条缺陷**必须**附截图、根因、修改建议、验收标准四要素。缺一不可。

## 七、协作礼仪

设计评审的失败模式往往不是技术问题，而是协作问题 [S8]：

### 1. 先肯定再建议

从对方做得好的地方切入（"信息层级清晰"），再引出改进点（"主按钮颜色可以再压低饱和度以避免在 hero 区夺走文案注意力"）。这是工程礼仪的基本要求。

### 2. 对事不对人

永远评价界面本身，而非设计者（"这个布局违反了亲密性法则" vs "你怎么连间距都不会"）。把"你"换成"这个界面"是基本动作。

### 3. 给可执行建议

不要停在"不好看 / 不高级 / 不够简洁"。每个批评必须挂载可执行修改（"按钮 padding 从 8px 提到 12px，使触控区达到 44px"）。

### 4. 区分硬红线与风格偏好

评审人最常见的错误是把个人偏好包装成"专业意见"。规则：所有反馈必须挂载一个客观依据——硬数字（对比度、像素数）、公认启发式、平台规范、心理学定律。无依据的意见退回到"个人偏好"层级，不进入修复队列。

### 5. 接受"驳回"

当被评审人引用硬规则反驳你的意见时（如"我们的间距是 4 的倍数，符合 8pt 网格"），接受驳回。专业评审不是辩论赛，目的是让界面变得更好，不是让评审人赢。

## 八、与 style-refactor 流程的衔接

评审的产出必须流入 style-refactor 流程，否则报告会变成"文档垃圾" [S8]：

```
评审产出 (Markdown 报告)
       ↓
拆解为修复任务 (一条缺陷 = 一个 Issue)
       ↓
按 P0/P1/P2 排入迭代
       ↓
执行修复 → 回归测试 → 关闭 Issue
```

### 1. 评审转任务的模板

每条 P0 / P1 缺陷对应一个 GitHub Issue：

- **标题**：`[评审 #日期] P0 对比度：登录页副标题色值未达标`
- **描述**：截图 + 缺陷描述 + 严重度 + 修复建议 + 验收标准（直接复用评审记录）
- **标签**：`design-review`, `p0-blocking`, `accessibility`
- **验收人**：原评审人或其指定代理

### 2. 防止"评审不闭环"

常见反模式：评审报告写得漂亮，但没有后续 Issue 跟踪。下次评审发现同一缺陷还在原地。解决方案：

- 评审报告归档时同步创建 Issues（自动化脚本可大幅降低工作量）
- 下一次评审先回顾上一轮 Issue 是否都已关闭
- 把"评审闭环率"作为团队的可见指标

## 真实任务

### 任务：对一个真实 SaaS 落地页完成评审

选择一个真实 SaaS 产品落地页（公开网站即可），完成以下工作：

1. 确认产品类型（落地页 / SaaS / 移动端），按 [docs/patterns/product-patterns.md](../../patterns/product-patterns.md) 锁定第一优先级约束。
2. 按 WCAG 2.2 AA 排查硬红线，用 WebAIM Contrast Checker 逐条验证 [S5]。
3. 按 Nielsen 10 启发式（重点 6 条）走查至少 1 个核心页面与 1 个关键交互（CTA、注册、定价）。
4. 套用 8 类视觉缺陷模式清单，记录至少 **10 条具体缺陷**（截图 + 描述 + 严重度 + 修复建议 + 验收标准）。
5. 按"先肯定再建议、对事不对人"的礼仪撰写评审报告，并列出每条缺陷对应的优先级（P0/P1/P2）。

约束：不得用"我觉得不好看"作为评审依据；每条反馈必须挂载具体指标或公认启发式。

## 失败模式（5 个常见错误）

| # | 错误表现 | 根因 | 修复方法 |
|---|---|---|---|
| 1 | 评审意见停留在"这个页面不好看 / 不够高级 / 感觉不对" | 把个人偏好包装成专业意见，未挂载硬指标或公认启发式 | 每条反馈必须附硬数字（对比度、像素数）、Nielsen 启发式编号、平台规范引用或心理学定律 |
| 2 | 把"我个人偏好蓝色"与"可用性问题"混为一谈，导致对方无法判断哪些必须改、哪些是口味之争 | 混淆了 Stakeholder review 与 Peer critique 的边界 | 评审开头明确类型；Stakeholder 评审允许业务偏好；Peer critique 评审只接受硬依据 |
| 3 | 评审报告只提问题不给修复建议，对方改不动或改了引入新问题 | 评审人未承担"指出 + 解法"的双重责任 | 每条缺陷必须配可执行建议（含色值、像素值、组件名）+ 验收标准 |
| 4 | 评审无截图证据，事后扯皮"我说过这里有问题" | 评审记录不完整，缺少可视化证据 | 强制要求每条缺陷附截图（圈出位置），无法截图的纯交互问题附录屏或步骤编号 |
| 5 | 用主观感受替代硬数字对比度审计 | 把"看起来够清晰"当作通过 WCAG 的依据 | 引入 WebAIM Contrast Checker [S5] 或 CI 自动化脚本，把对比度数字写进 PR 描述 |

## 本章验收

1. **三种评审辨析**：你的团队上线了一个新的订阅定价页。请说明 Stakeholder review / Peer critique / Heuristic evaluation 三种评审的评审人构成、产出差异，以及你建议的执行顺序与理由。
2. **硬红线判定**：给一个真实界面（或截图），请列出至少 5 条 P0 硬红线检查项，并说明每条的判定依据（WCAG 条款编号 / 平台规范）。
3. **协作礼仪应用**：你作为 Peer critique 评审人，对方提交的设计在 8pt 网格、对比度上完全合规，但主色用了与品牌色不同的色相，且 hero 区 CTA 文案过长。请写出你的评审意见开头两段（先肯定再建议，对事不对人，给可执行建议）。
